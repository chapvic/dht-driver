Главное нововведение: файл конфигурации /etc/default/dht
================================================================================

Драйвер теперь читает опциональный файл конфигурации при загрузке модуля.
Если файл отсутствует, драйвер загружается со значениями по умолчанию.
Это позволяет автоматически регистрировать сенсоры, включать отладку и
настраивать автоопрос без ручной записи в procfs после insmod.

Формат файла конфигурации
--------------------------

Строки, начинающиеся с '#', и пустые строки игнорируются.
Регистр имён опций не учитывается (strncasecmp).

Глобальные опции:

  DEBUG                  Включить отладку при загрузке (эквивалент DEBUG=1)
  DEBUG=0                Явно выключить отладку
  DEBUG=1                Явно включить отладку

  AUTO_INTERVAL=N        Глобальный интервал автоопроса в секундах (2-60)
                         Запускает автоопрос для всех зарегистрированных
                         сенсоров, у которых не задан индивидуальный интервал
  AUTO_INTERVAL=-1       Отключить глобальный автоопрос

Регистрация сенсоров:

  SENSOR=<pin>           Зарегистрировать сенсор на указанном BCM-пине
                         без автоопроса

  SENSOR=<pin>,<N>       Зарегистрировать сенсор с индивидуальным
                         интервалом автоопроса N секунд (2-60)
                         Если активен глобальный AUTO_INTERVAL, индивидуальный
                         интервал имеет приоритет

Пример файла /etc/default/dht:

  # Конфигурация DHT-драйвера
  DEBUG=1
  AUTO_INTERVAL=10
  SENSOR=4               # DHT22 на GPIO4, использует глобальный интервал
  SENSOR=17,5            # DHT11 на GPIO17, опрос каждые 5 секунд
  SENSOR=22              # Сенсор на GPIO22, без автоопроса

Обработка ошибок
----------------

Если файл содержит недопустимую опцию или недопустимое значение, драйвер
выводит соответствующее сообщение в dmesg (KERN_ERR) и продолжает обработку
остальных строк. Ошибки в конфигурации не предотвращают загрузку драйвера.

| Ситуация                          | Сообщение в dmesg                          |
|-----------------------------------|--------------------------------------------|
| Файл отсутствует                  | (тихо, отладочное сообщение при DEBUG=1)   |
| Неизвестная опция                 | config: unknown option 'XXX'               |
| Недопустимый пин                  | config: SENSOR pin 'XX' invalid (0-27)     |
| Недопустимый интервал сенсора     | config: SENSOR interval 'XX' invalid       |
|                                   | (2-60 or -1)                               |
| Недопустимое значение DEBUG       | config: DEBUG='XX' invalid                 |
|                                   | (expected 0 or 1)                          |
| Недопустимое значение             | config: AUTO_INTERVAL='XX' is not a        |
| AUTO_INTERVAL                     | valid integer                              |
| AUTO_INTERVAL вне диапазона       | config: AUTO_INTERVAL=XX out of range      |
|                                   | (2-60 or -1)                               |

Семантика порядка опций
------------------------

Опции обрабатываются сверху вниз, что влияет на результат:

1. AUTO_INTERVAL до SENSOR:
   Сенсор при регистрации обнаруживает активный глобальный интервал
   и автоматически включается в глобальный автоопрос.

2. AUTO_INTERVAL после SENSOR:
   Сенсор сначала регистрируется без опроса, затем AUTO_INTERVAL
   запускает poll threads для всех уже зарегистрированных сенсоров.

Оба сценария работают корректно.

Изменения в коде
----------------

Новые функции:

  dht_do_register(int pin, int interval)
    Логика регистрации сенсора извлечена из export_write в отдельную
    функцию. Выполняет проверку дубликатов, запрос GPIO, выделение памяти,
    создание procfs-записей, первичное измерение, добавление в список
    и запуск автоопроса. Если interval в диапазоне 2-60 и глобальный
    автоопрос выключен, запускает per-sensor poll thread.
    Возвращает 0 при успехе, отрицательный errno при ошибке.

  dht_parse_config_line(const char *line)
    Разбор одной строки конфигурации. Поддерживает формат ключ=значение,
    комментарии '#', нечувствительность к регистру имён опций.
    Вызывает dht_do_register() для SENSOR, WRITE_ONCE(dht_debug) для DEBUG,
    и установку global_auto_interval для AUTO_INTERVAL.

  dht_load_config(void)
    Чтение /etc/default/dht через VFS (filp_open + kernel_read).
    Буфер 4096 байт выделяется через kmalloc — нет проблем со стеком.
    Если файл отсутствует, драйвер загружается тихо со значениями по
    умолчанию. Поддерживает строки в формате Unix (\n) и DOS (\r\n).
    Вызывается в конце dht_driver_init() после создания procfs.

Изменённые функции:

  export_write()
    Превращена в тонкую обёртку: парсит пин из user-space, вызывает
    dht_do_register(pin, -1). Возвращает count или ошибку.

  dht_driver_init()
    Добавлен вызов dht_load_config() после создания всех procfs-записей
    и перед финальным логом. Это гарантирует, что сенсоры, зарегистриро-
    ванные из конфига, получат корректные proc-записи.

Новые константы:

  CONFIG_PATH       "/etc/default/dht"   Путь к файлу конфигурации
  CONFIG_BUF_LEN    4096                 Максимальный размер буфера файла
  CONFIG_LINE_LEN   256                  Максимальная длина одной строки

Технические детали
------------------

  - Файл читается через kernel_read() с loff_t pos = 0, что совместимо
    с kernel 6.x API (kernel_read теперь принимает loff_t* вместо ssize_t*).
  - Используется strscpy для безопасного копирования строк.
  - Используется strim для удаления пробелов в начале и конце строки.
  - Используется kstrtoint для парсинга числовых значений.
  - Буфер чтения в куче (kmalloc) — frame size функции парсинга ~320 байт
    вместо 4112, что устраняет предупреждение -Wframe-larger-than.
  - Поддержка комментариев в любом месте строки через strim (только
    полные строки-комментарии, начинающиеся с '#').

Версия 2.6

Главное нововведение: совместное использование /proc/sensors
================================================================

Драйвер корректно сосуществует с другими сенсорными драйверами, которые
могут использовать директорию /proc/sensors.

Проблема
--------

В v2.5 драйвер безусловно создавал /proc/sensors при загрузке и удалял
при выгрузке. Если другой драйвер (например, lm-sensors) уже создал
эту директорию, возникал конфликт: DHT-драйвер либо не мог создаться,
либо удалял чужую директорию при выгрузке.

Решение
-------

  1. Флаг we_created_parent: драйвер запоминает, создал ли он
     /proc/sensors сам, или директория уже существовала.

  2. Smart init: при загрузке драйвер сначала пытается создать
     /proc/sensors. Если proc_mkdir возвращает NULL (директория уже
     существует), он получает её через proc_mkdir_data или просто
     продолжает, используя существующую.

  3. Smart exit: при выгрузке драйвер удаляет /proc/sensors только
     если флаг we_created_parent = true. Проверка на пустоту
     директории через VFS (vfs_inode) предотвращает удаление, если
     внутри остались записи других драйверов.

  4. Ownership flag: atomically_set для thread-safety.

Сценарии сосуществования:

| Сценарий                      | Поведение                                 |
|-------------------------------|-------------------------------------------|
| DHT загружается первым        | Создаёт /proc/sensors, устанавливает      |
|                               | we_created_parent = true                  |
| Другой драйвер загружается    | Создаёт /proc/sensors/<имя>,              |
| после DHT                     | DHT не мешает                             |
| Другой драйвер выгружается    | Удаляет только свою поддиректорию,        |
|                               | /proc/sensors остаётся                    |
| DHT выгружается               | Проверяет we_created_parent и пустоту     |
|                               | /proc/sensors. Если DHT создал директорию |
|                               | и она пуста — удаляет. Иначе оставляет.   |

Безопасная выгрузка модуля
==========================

Три слоя защиты от выгрузки во время активных операций:

  1. try_module_get() в dht_proc_open: счётчик ссылок модуля
     увеличивается при открытии любого procfs-файла. rmmod не может
     выгрузить модуль, пока хотя бы один файл открыт.

  2. dht_proc_release уменьшает счётчик при закрытии файла.

  3. atomic_t dht_exiting: устанавливается в dht_driver_exit() и
     проверяется в dht_proc_open(). Новые открытия procfs-файлов
     отклоняются с -ENODEV после начала выгрузки.

Двухфазная выгрузка:

  Фаза 1: dht_driver_exit()
    - Устанавливает dht_exiting (отклоняет новые procfs-операции)
    - Блокирует list_lock
    - Переносит все сенсоры из sensor_list в tmp_list
    - Разблокирует list_lock

  Фаза 2: Очистка (вне блокировки)
    - Для каждого сенсора: остановка poll thread (kthread_stop),
      уничтожение mutex, освобождение памяти
    - Удаление procfs-записей
    - Удаление /proc/sensors/dht и (возможно) /proc/sensors

Rate limiting для всех измерений
================================

Ограничение частоты измерений (минимум 2 секунды между измерениями)
применяется ко всем типам измерений:

  - Ручные измерения (запись в /proc/sensors/dht/gpio<pin>/measure):
    Если интервал слишком короткий, возвращается ERR_TOO_SOON.

  - Автоопрос (poll thread):
    Если интервал слишком короткий, измерение тихо пропускается,
    последние данные сохраняются.

  - Первичное измерение при регистрации (export_write / config):
    Rate limiting не применяется, так как это первое измерение.

Определение GPIO-чипа (Pi 3/4/5)
================================

Трёхстадийный поиск GPIO-дескриптора по BCM-номеру:

  Стадия 1 (быстрый путь):
    Если cached_chip_base известен, вычисляет global = base + bcm_pin.
    Используется после первой успешной регистрации.

  Стадия 2 (прямой поиск):
    gpio_to_desc(bcm_pin) — работает на Pi 3/4, где base = 0.
    При успехе кэширует base для будущих вызовов.

  Стадия 3 (полный скан):
    Перебор всех GPIO-номеров 0..2048 для поиска чипа Raspberry Pi
    (pinctrl-rp1, pinctrl-bcm2835, pinctrl-bcm2711, pinctrl-bcm2712),
    где локальный offset совпадает с запрошенным BCM-пином.
    Нужен на Pi 5, где base может быть 512+.

Кэширование base — write-once: устанавливается при первой регистрации,
затем только читается через READ_ONCE.

--------------------------------------------------------------------------------
Версия 2.5
--------------------------------------------------------------------------------

Начальный релиз драйвера DHT11/DHT22/AM2302.

Основные возможности:

  - Динамическая регистрация/удаление сенсоров через procfs (export/unexport)
  - Per-sensor proc-записи: pin, interval, measure, status_code,
    status_text, value, info, timestamp
  - Фоновый поток опроса с настраиваемым интервалом (per-sensor)
  - Глобальный режим автоопроса с общим интервалом
  - Наносекундная точность таймингов для надёжного чтения на всех Pi
  - Определение типа сенсора (DHT11/DHT22/AM2302) после первого измерения
  - Формат данных: H=<влажность>\nT=<температура>\n
    (DHT11 — целые числа, DHT22 — с десятыми, x10 масштабирование)
  - Совместимость с kernel 5.x - 6.x (proc_ops / file_operations,
    pde_data / PDE_DATA)
  - Максимальное количество сенсоров: 32
  - Диапазон BCM-пинов: 0-27
  - Диапазон интервалов автоопроса: 2-60 секунд
  - Максимальное количество попыток чтения: 3
  - Задержка между попытками: 100 мс

================================================================================
Совместимость
================================================================================

  Ядро Linux:    5.6+ (требуется для struct proc_ops)
                 5.17+ (pde_data вместо PDE_DATA)
                 протестировано на 6.18.50+rpt-rpi-v8 (Raspberry Pi OS,
                 kernel 6.18, arm64)

  Архитектура:   arm64 (aarch64)
                 arm32 (armhf) — должно работать, не тестировалось

  Оборудование:  Raspberry Pi 5  (pinctrl-rp1, base >= 512)
                 Raspberry Pi 4  (pinctrl-bcm2711)
                 Raspberry Pi 3  (pinctrl-bcm2835)
                 Raspberry Pi Zero 2 W (pinctrl-bcm2835)

  Датчики:       DHT11  (целочисленные значения, точность 1°C / 1%)
                 DHT22  (десятичные значения, точность 0.1°C / 0.1%)
                 AM2302 (DHT22 в отдельном корпусе, тот же протокол)

  Обратная совместимость: v2.7 полностью совместима с конфигурациями,
                 созданными для v2.5/v2.6. Файл конфигурации /etc/default/dht
                 является опциональным дополнением — все существующие procfs-
                 команды продолжают работать без изменений.
