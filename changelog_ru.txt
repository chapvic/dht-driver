РЕЛИЗ V2.6 — ОСНОВНЫЕ ИЗМЕНЕНИЯ
================================================================================

Главное новшество v2.6 — безопасное совместное использование каталога /proc/sensors
с другими драйверами датчиков.

Раньше драйвер безусловно создавал и удалял /proc/sensors, что приводило к
удалению записей других драйверов при выгрузке DHT-модуля. Теперь драйвер
корректно определяет, кто создал каталог, и удаляет его только если внутри
не осталось чужих подкаталогов.

Это первый шаг к экосистеме драйверов датчиков, совместно использующих
общий каталог /proc/sensors.

v2.6 (20 сентября 2026 г.) — СОВМЕСТНОЕ ИСПОЛЬЗОВАНИЕ /proc/sensors
--------------------------------------------------------------------------------

ПРОБЛЕМА
--------
В версии 2.5.2 при инициализации драйвер вызывал remove_proc_subtree("sensors")
если каталог /proc/sensors уже существовал — это уничтожало все записи других
драйверов. При выгрузке каталог /proc/sensors удалялся безусловно.

Это делало невозможным одновременную работу нескольких драйверов датчиков,
использующих /proc/sensors как общий родительский каталог.

РЕШЕНИЕ
-------
Реализованы три механизма:

1. Флаг владения we_created_parent
   - Устанавливается в true только если proc_mkdir("sensors", NULL) вернул
     валидный handle (мы создали каталог).
   - Если возвращён NULL — каталог уже существует, флаг остаётся false,
     proc_parent устанавливается в NULL.

2. Умное создание в dht_driver_init:
   - proc_mkdir("sensors", NULL) → успех → we_created_parent = true,
     создаём "dht" как дочерний каталог.
   - proc_mkdir("sensors", NULL) → NULL → каталог уже есть,
     создаём через полный путь proc_mkdir("sensors/dht", NULL) —
     ядро само находит существующий родитель через xlate_proc_name().

3. Умное удаление в dht_driver_exit:
   - proc_remove(proc_dir) — удаляем только своё дерево /proc/sensors/dht/.
   - Если we_created_parent && proc_parent:
     Проверяем пустоту через VFS (dht_proc_dir_is_empty):
       - Пусто → proc_remove(proc_parent) + лог "removed (was empty)"
       - Есть чужие подкаталоги → оставляем +
         лог "not removed (other drivers using it)"
   - Если !we_created_parent — вообще не трогаем /proc/sensors.

4. remove_proc_subtree полностью удалён — больше не уничтожает чужие записи.

ВСПОМОГАТЕЛЬНАЯ ФУНКЦИЯ dht_proc_dir_is_empty
--------------------------------------------
Использует VFS-интерфейс (filp_open + iterate_dir + filp_close), так как
struct proc_dir_entry непрозрачна в новых ядрах — поле ->subdir недоступно.
Callback dht_dir_filldir возвращает bool (требование ядра 6.x).

СЦЕНАРИИ СОВМЕСТНОЙ РАБОТЫ
--------------------------

┌─────────────────────────┬────────────────────┬──────────────────────────────────────────┐
│ Кто грузится первым     │ we_created_parent  │ Что происходит при выгрузке DHT          │
├─────────────────────────┼────────────────────┼──────────────────────────────────────────┤
│ DHT грузится первым     │ true               │ Удаляет dht, проверяет пустоту sensors,  │
│                         │                    │ удаляет sensors если пуст                │
├─────────────────────────┼────────────────────┼──────────────────────────────────────────┤
│ Другой драйвер первым   │ false              │ Удаляет только dht,                      │
│                         │                    │ /proc/sensors не трогает                 │
└─────────────────────────┴────────────────────┴──────────────────────────────────────────┘


v2.5.2 — БЕЗОПАСНАЯ ВЫГРУЗКА МОДУЛЯ
--------------------------------------------------------------------------------

ПРОБЛЕМА
--------
При выгрузке модуля (rmmod) во время открытых procfs-файлов или активных
kthread_poll потоков мог возникать kernel panic или use-after-free:
  1. struct proc_ops не содержала .owner, ядро не удерживало refcount модуля.
  2. Глобальные proc-записи оставались доступны во время kthread_stop.
  3. Poll-потоки могли обращаться к памяти модуля после выгрузки.

РЕШЕНИЕ — ТРИ СЛОЯ ЗАЩИТЫ
-------------------------

Слой 1: Учёт ссылок модуля (try_module_get / module_put)
  - Обёртки dht_single_open / dht_single_release на всех proc-записях.
  - dht_single_open: проверяет dht_exiting, вызывает try_module_get,
    затем single_open.
  - dht_single_release: вызывает single_release, затем module_put.
  - Гарантирует: rmmod получает EBUSY пока хоть один proc-файл открыт.
  - Обёрнуты все 13 proc-записей (9 per-sensor + 4 global).

Слой 2: Флаг atomic_t dht_exiting
  - Устанавливается в 1 в начале dht_driver_exit.
  - dht_single_open проверяет флаг и возвращает -ENODEV если идёт выгрузка.
  - Запрещает новые открытия proc-файлов до начала очистки.

Слой 3: Двухфазная очистка
  Фаза 1 (подготовка):
    - atomic_set(&dht_exiting, 1) — блокируем новые открытия.
    - proc_remove(proc_dir) — удаляем всё дерево /proc/sensors/dht/.
  Фаза 2 (завершение):
    - Останавливаем poll-потоки (kthread_stop для каждого).
    - Удаляем /proc/sensors (если мы его создали и он пуст).
    - Логирование завершения.


v2.5.1 — ОГРАНИЧЕНИЕ ЧАСТОТЫ ОПРОСА
--------------------------------------------------------------------------------

ПРОБЛЕМА
--------
Ручные измерения имели rate limiting (минимум 2 секунды между запросами),
но автоопрос мог читать датчик без ограничений, нарушая временные
характеристики DHT-сенсоров (минимум 2 секунды между чтениями).

РЕШЕНИЕ
-------
Rate limiting (MEAS_MIN_GAP = 2 секунды) распространён на ВСЕ измерения:
  - Ручные: возвращают ERR_TOO_SOON пользователю.
  - Автоопрос: тихо пропускают цикл, сохраняя последние данные.

ПОЧЕМУ ЭТО ВАЖНО
----------------
DHT11/DHT22 технически требуют минимум 2 секунды между чтениями.
Без rate limiting частый опрос приводил к ошибкам чтения и нестабильным
данным. Теперь драйвер соблюдает это ограничение аппаратуры.


v2.5 — НАЧАЛЬНЫЙ РЕЛИЗ
--------------------------------------------------------------------------------

Основные возможности:
  - Динамическая регистрация/удаление датчиков через procfs (export/unexport)
  - Per-sensor proc-записи: температура, влажность, статус, конфигурация
  - Фоновый поток опроса с настраиваемым интервалом
  - Глобальный режим автоопроса с общим интервалом
  - Кэширование базы GPIO-чипа для быстрой регистрации на Pi 3/4/5
  - Наносекундная точность тайминга для надёжного чтения на всех моделях Pi
  - Rate limiting для всех измерений (ручных и автоопроса)
  - Безопасная выгрузка с учётом ссылок модуля
  - Совместное использование /proc/sensors (v2.6)

ИЗВЕСТНЫЕ ОГРАНИЧЕНИЯ
================================================================================

  - Максимум 32 одновременно зарегистрированных датчика (MAX_SENSORS)
  - Диапазон BCM-пинов: 0-27 (MAX_PIN_NUM)
  - Минимум 2 секунды между измерениями (ограничение аппаратуры DHT)
  - Автоопределение типа датчика только после первого успешного измерения
  - Драйвер занимает GPIO-пин на всё время регистрации
  - Нет поддержки прерываний — только polling
  - Rate limiting применяется к каждому датчику индивидуально
