## Обзор

Драйвер DHT предоставляет интерфейс на основе procfs для чтения температуры и влажности с датчиков DHT11, DHT22 и AM2302, подключённых к GPIO-пинам Raspberry Pi.

Ключевые возможности:

- Динамическая регистрация датчиков через procfs (`export`/`unexport`)
- Индивидуальные proc-записи для каждого датчика: температура, влажность, статус и конфигурация
- Фоновый поток опроса с настраиваемым интервалом (индивидуальным или глобальным)
- Ручной запуск измерения через procfs
- Наносекундная точность измерения импульсов для надёжного чтения на всех моделях Pi
- Кэширование базы GPIO-чипа для быстрой регистрации нескольких датчиков на Pi 3/4/5
- Ограничение частоты измерений (rate limiting) для всех типов измерений
- Безопасная выгрузка модуля со счётчиком ссылок (`kref`)
- Разделение каталога `/proc/sensors`: сосуществует с другими драйверами датчиков
- Файл конфигурации: опциональный `/etc/default/dht` для авто-регистрации при загрузке
- Совместимость с ядром: 5.0 — 6.18+ (с compile-time адаптерами API)
- Поддержка DKMS: автоматическая пересборка при обновлении ядра

## Архитектура протокола DHT

Датчики DHT11/DHT22/AM2302 используют проприетарный однопроводной двунаправленный протокол. Хост (MCU) инициирует обмен, а датчик отвечает 40 битами данных (5 байт).

### Последовательность обмена

1. **Старт-сигнал хоста**: MCU удерживает линию данных в низком уровне не менее 18 мс (драйвер использует 20 мс)
2. **Освобождение линии хостом**: MCU переключает линию в режим ввода; подтягивающий резистор переводит линию в высокий уровень
3. **Ответ датчика** (через 20-40 мкс после освобождения):
   - Низкий импульс ~80 мкс
   - Высокий импульс ~80 мкс
4. **Передача данных** (40 бит):
   - Каждый бит: ~50 мкс низкий импульс, затем высокий импульс, длительность которого кодирует значение
   - **Бит 0**: высокий импульс ~26 мкс
   - **Бит 1**: высокий импульс ~70 мкс
5. **Конец кадра**: линия возвращается в состояние высокого уровня (покой)

### Кодирование битов

| Значение бита | Низкий импульс | Высокий импульс |
|---------------|----------------|-----------------|
| 0             | ~50 мкс        | ~26 мкс         |
| 1             | ~50 мкс        | ~70 мкс         |

Драйвер использует **порог 40 мкс** (`BIT_THRESHOLD = 40000 ns`) для различения 0 и 1.

### 40-битный кадр данных

| Байт | Поле                | Формат DHT11        | Формат DHT22        |
|------|--------------------|---------------------|---------------------|
| 0    | Целая влажности    | 0-100 (целое)      | Старший байт RH     |
| 1    | Дробная влажности  | 0 (всегда ноль)     | Младший байт RH     |
| 2    | Целая температуры  | 0-50 (целое)       | Старший байт T (бит 7 = знак) |
| 3    | Дробная темп-ры    | 0 (всегда ноль)     | Младший байт T      |
| 4    | Контрольная сумма  | (byte0+byte1+byte2+byte3) & 0xFF | То же |

**DHT11** передаёт только целые значения (дробные байты всегда 0). Значения масштабируются x10 в драйвере для единообразия единиц.

**DHT22/AM2302** передаёт 16-битные значения, масштабированные x10: влажность как `(byte0 << 8) | byte1`, температура как `((byte2 & 0x7F) << 8) | byte3`. Бит 7 байта 2 — знаковый бит для отрицательных температур.

### Временные параметры

| Параметр                  | Значение     | Описание                                   |
|---------------------------|--------------|--------------------------------------------|
| Старт-сигнал (низкий)     | 20 мс        | Хост удерживает линию в низком уровне       |
| Задержка ответа датчика   | 20-40 мкс    | После освобождения линии хостом             |
| Низкий импульс бита       | ~50 мкс      | Фиксированный низкий перед каждым битом    |
| Высокий импульс (0)       | ~26 мкс      | Ниже `BIT_THRESHOLD` (40 мкс)              |
| Высокий импульс (1)       | ~70 мкс      | Выше `BIT_THRESHOLD` (40 мкс)              |
| Тайм-аут импульса         | 300 мкс      | `PULSE_TIMEOUT_NS` — отмена при превышении  |
| Общая длительность кадра  | ~4 мс        | 40 бит + рукопожатие                       |
| Мин. интервал между чтениями | 2 с       | `MEAS_MIN_GAP` — время восстановления датчика|

Драйвер отключает прерывания (`local_irq_save`/`local_irq_restore`) во время bit-bang чтения, чтобы предотвратить искажение временных интервалов обработчиками прерываний и переключениями контекста. На Raspberry Pi 3 обработчики прерываний USB/SDIO/таймера могут занимать 100-300 мкс, превышая `PULSE_TIMEOUT_NS` и повреждая чтение. Это следует паттерну, используемому драйверами `w1-gpio` и `i2c-gpio` bit-bang в основной ветке ядра.

| Датчик  | Диапазон температур | Диапазон влажности | Точность (T) | Точность (H) | Тип      |

## Подключение

### GPIO-разъём Raspberry Pi

Подключите пин данных датчика к любому доступному GPIO-пину (нумерация BCM). Драйвер принимает номера BCM пинов 0-27.

```
Датчик DHT        Raspberry Pi
---------        ------------
VCC (пин 1)  →   3.3V (пин 1 или 17)
DATA         →   GPIO-пин на ваш выбор (напр., GPIO4 = пин 7)
GND (пин 4)  →   GND (пин 6 или 9)
```

### Подтягивающий резистор

Большинство модулей датчиков DHT имеют встроенный подтягивающий резистор (4.7k-10k). При использовании отдельного датчика:

- Подключите резистор 4.7кОм-10кОм между DATA и VCC (3.3В)
- Без подтягивающего резистора показания будут нестабильными или чтение не удастся

### Выбор пина

- Поддерживаются любые BCM GPIO-пины 0-27
- Избегайте пинов со специальными функциями (напр., GPIO14/15 = UART, GPIO3 = I2C SDA), если эти интерфейсы используются
- GPIO4 — популярный выбор для датчиков DHT на Raspberry Pi

## Быстрый старт

```bash
# 1. Склонируйте или скопируйте файлы драйвера в директорию
cd dht-driver

# 2. Соберите
make

# 3. Загрузите модуль
sudo insmod dht.ko

# 4. Зарегистрируйте датчик на GPIO4
echo 4 | sudo tee /proc/sensors/dht/export

# 5. Считайте температуру и влажность
cat /proc/sensors/dht/gpio4/value

# 6. Включите автоопрос каждые 5 секунд
echo 5 | sudo tee /proc/sensors/dht/gpio4/interval

# 7. Или включите глобальный автоопрос для всех датчиков
echo 10 | sudo tee /proc/sensors/dht/auto_interval

# 8. Проверьте версию драйвера
cat /proc/sensors/dht/version

# 9. Выгрузите по завершении
sudo rmmod dht
```

## Сборка и установка

### Предварительные требования

```bash
# Raspberry Pi OS / Debian / Ubuntu
sudo apt install build-essential linux-headers-$(uname -r)
```

### Локальная сборка

```bash
make            # запускает pre-build проверки, затем собирает dht.ko
make check      # только pre-build проверки
make modules    # сборка без проверок
make clean      # удалить артефакты сборки
```

### Установка (локальная)

```bash
make install    # собирает, устанавливает в /lib/modules/$(uname -r)/, запускает depmod
sudo modprobe dht
```

Модуль устанавливается в `/lib/modules/$(uname -r)/updates/` через Kbuild. Это стандартное расположение для out-of-tree модулей, имеющее приоритет над `/kernel/` при поиске через `modprobe`.

### Удаление

```bash
make uninstall   # ищет и удаляет dht.ko из всех директорий модулей
sudo modprobe -r dht
```

Цель `uninstall` использует `find` для поиска по всем подкаталогам в `/lib/modules/$(uname -r)/` (включая `updates/`, `kernel/`, `extra/`), корректно удаляя модуль независимо от того, куда его поместил Kbuild.

### Кросс-компиляция

```bash
# Пример: сборка на x86 для Raspberry Pi 5 (arm64)
make ARCH=arm64 \
     CROSS_COMPILE=aarch64-linux-gnu- \
     KDIR=/path/to/rpi-kernel/build

# Установка в примонтированную целевую файловую систему
make ARCH=arm64 \
     CROSS_COMPILE=aarch64-linux-gnu- \
     KDIR=/path/to/rpi-kernel/build \
     INSTALL_MOD_PATH=/mnt/rpi-root \
     install
```

### Цели Make

| Цель           | Описание                                         |
|----------------|--------------------------------------------------|
| `make`         | Pre-build проверки, затем сборка модуля          |
| `make check`   | Только pre-build проверки (заголовки, версия)    |
| `make modules` | Сборка `dht.ko` без проверок                      |
| `make clean`   | Удаление артефактов сборки                       |
| `make install` | Сборка, установка в `/lib/modules/...`, `depmod` |
| `make uninstall` | Поиск и удаление `dht.ko` из всех директорий    |
| `make help`    | Показать доступные цели и переменные             |

## Установка через DKMS

DKMS (Dynamic Kernel Module Support) автоматически пересобирает модуль при обновлении ядра. Это избавляет от необходимости вручную пересобирать после каждого `apt upgrade`.

### Предварительные требования

```bash
sudo apt install dkms
```

### Установка

```bash
# 1. Скопируйте файлы драйвера в дерево исходников DKMS
sudo mkdir -p /usr/src/dht-2.0
sudo cp dht.c Makefile dkms.conf /usr/src/dht-2.0/

# 2. Зарегистрируйте модуль в DKMS
sudo dkms add dht/2.0

# 3. Соберите и установите
sudo dkms install dht/2.0

# 4. Загрузите модуль
sudo modprobe dht
```

### Проверка

```bash
# Проверьте статус DKMS
sudo dkms status
# Ожидаемый вывод: dht/2.0: installed

# Проверьте, что модуль загружен
lsmod | grep dht
cat /proc/sensors/dht/version
```

### Автоматическая пересборка

С `AUTOINSTALL="yes"` в `dkms.conf` модуль автоматически пересобирается при установке нового ядра. Ручное вмешательство не требуется.

### Обновление до новой версии драйвера

```bash
# 1. Удалите старую версию
sudo dkms remove dht/2.0 --all

# 2. Скопируйте новые файлы
sudo cp dht.c Makefile dkms.conf /usr/src/dht-2.0/

# 3. Переустановите
sudo dkms install dht/2.0
```

### Полное удаление

```bash
sudo dkms remove dht/2.0 --all
sudo rm -rf /usr/src/dht-2.0
```

### dkms.conf

```ini
PACKAGE_NAME="dht"
PACKAGE_VERSION="2.0"
BUILT_MODULE_NAME[0]="dht"
DEST_MODULE_LOCATION[0]="/updates"
AUTOINSTALL="yes"
MAKE[0]="make -C ${kernel_source_dir} M=${dkms_tree}/${PACKAGE_NAME}/${PACKAGE_VERSION}/build modules"
CLEAN="make -C ${kernel_source_dir} M=${dkms_tree}/${PACKAGE_NAME}/${PACKAGE_VERSION}/build clean"
```

## Файл конфигурации

Драйвер читает опциональный файл конфигурации `/etc/default/dht` при загрузке. Если файл отсутствует, драйвер загружается с настройками по умолчанию.

### Формат

Строки, начинающиеся с `#`, и пустые строки игнорируются. Неизвестные опции и некорректные значения вызывают предупреждения в `dmesg`.

### Опции

**Глобальные опции:**

| Опция                | Описание                                               |
|----------------------|--------------------------------------------------------|
| `DEBUG`              | Включить отладку (то же, что `DEBUG=1`)                 |
| `DEBUG=0|1`          | Явно отключить/включить отладку                         |
| `AUTO_INTERVAL=n`    | Глобальный интервал автоопроса в секундах (2-60)        |

**Регистрация датчиков:**

| Опция                | Описание                                               |
|----------------------|--------------------------------------------------------|
| `SENSOR=<pin>`       | Зарегистрировать датчик на указанном BCM-пине          |
| `SENSOR=<pin>,<n>`   | Зарегистрировать с индивидуальным интервалом (2-60 с)   |

### Пример

```bash
# /etc/default/dht
DEBUG=1
AUTO_INTERVAL=10
SENSOR=4             # DHT22 на GPIO4, использует глобальный интервал
SENSOR=17,5          # DHT11 на GPIO17, опрос каждые 5 секунд
SENSOR=22            # Датчик на GPIO22, без автоопроса
```

### strict_config

При `strict_config=1` любая ошибка в файле конфигурации (некорректное значение, неизвестная опция, неудачная регистрация датчика) прерывает загрузку модуля с `-EINVAL` и полным откатом. При `strict_config=0` (по умолчанию) ошибки логируются в `dmesg`, и драйвер продолжает загрузку.

## Интерфейс procfs

### Глобальные записи

```
/proc/sensors/dht/
  debug         (rw) - отладка: 0 = выкл (по умолчанию), 1 = вкл
  version       (r)  - версия драйвера
  export        (w)  - записать номер BCM-пина для регистрации датчика
  unexport      (w)  - записать номер BCM-пина для отмены регистрации
  auto_interval (rw) - глобальный интервал автоопроса (2-60, -1 = выкл)
```

### Записи датчика

```
/proc/sensors/dht/gpio<pin>/
  pin           (r)  - номер BCM GPIO-пина
  interval      (rw) - интервал автоопроса в секундах (2-60, -1 = выкл)
  measure       (w)  - записать "1" для запуска измерения
  status_code   (r)  - код ошибки (0 = успех)
  status_text   (r)  - описание ошибки
  value         (r)  - "H=<влажность>\nT=<температура>\n"
  info          (r)  - тип датчика + время регистрации
  timestamp     (r)  - Unix-метка времени последнего измерения
```

### Права доступа

| Запись           | Права | Описание                          |
|------------------|-------|-----------------------------------|
| debug            | 0644  | Чтение: все, запись: root         |
| version          | 0444  | Чтение: все                       |
| export/unexport  | 0200  | Запись: только root               |
| auto_interval    | 0644  | Чтение: все, запись: root         |
| pin/status/value | 0444  | Чтение: все                       |
| interval         | 0644  | Чтение: все, запись: root         |
| measure          | 0200  | Запись: только root               |

## Автоматический опрос

### Индивидуальный интервал

```bash
echo 5 | sudo tee /proc/sensors/dht/gpio4/interval
# Опрос каждые 5 секунд
```

```bash
echo -1 | sudo tee /proc/sensors/dht/gpio4/interval
# Остановить автоопрос для этого датчика
```

### Глобальный интервал

```bash
echo 10 | sudo tee /proc/sensors/dht/auto_interval
# Все датчики опрашиваются каждые 10 секунд
```

```bash
echo -1 | sudo tee /proc/sensors/dht/auto_interval
# Остановить глобальный автоопрос
```

Глобальный интервал имеет приоритет над индивидуальным. При включении глобального автоопроса запускаются потоки для всех зарегистрированных датчиков, у которых ещё нет активного потока.

## Ручное измерение

```bash
echo 1 | sudo tee /proc/sensors/dht/gpio4/measure
```

Ручное измерение доступно только когда автоопрос отключён (и индивидуальный интервал = -1, и глобальный = -1). В противном случае возвращается ошибка `ERR_AUTO_MODE`.

Ручные измерения подчиняются rate limiting: не менее `MEAS_MIN_GAP` (2 секунды) должно пройти с момента последней попытки.

## Определение типа датчика

Драйвер автоматически определяет тип датчика по формату данных:

| Условие                              | Тип    |
|--------------------------------------|--------|
| Дробные байты влажности/темп-ры = 0  | DHT11  |
| Любое ненулевое значение в дробных байтах | DHT22  |

Тип определяется после первого успешного измерения и отображается в записи `info`.

## Примеры на Python

### Чтение данных

```python
def read_dht(pin=4):
    with open(f'/proc/sensors/dht/gpio{pin}/value') as f:
        data = f.read()
    temp = float(data.split('T=')[1].strip())
    hum = float(data.split('H=')[1].split('\n')[0])
    return temp, hum

temp, hum = read_dht(4)
print(f"Temperature: {temp}°C, Humidity: {hum}%")
```

### Проверка статуса

```python
def check_status(pin=4):
    with open(f'/proc/sensors/dht/gpio{pin}/status_code') as f:
        code = int(f.read().strip())
    if code == 0:
        return True, "OK"
    with open(f'/proc/sensors/dht/gpio{pin}/status_text') as f:
        text = f.read().strip()
    return False, text

ok, msg = check_status(4)
print(f"Status: {msg}")
```

## Архитектура

### Поток выполнения

1. **Загрузка модуля** (`dht_driver_init`):
   - Создание procfs-дерева (`/proc/sensors/dht/`)
   - Чтение файла конфигурации (`/etc/default/dht`)
   - Авто-регистрация датчиков из конфигурации

2. **Регистрация датчика** (`dht_do_register`):
   - Поиск GPIO-дескриптора через `gpiod_get_index`
   - Создание procfs-записей (`dht_create_sensor_proc`)
   - Начальное измерение для проверки датчика
   - Запуск poll thread, если интервал != -1

3. **Фоновый опрос** (`dht_poll_thread_fn`):
   - Цикл с `kthread_should_stop()` проверкой
   - Вызов `dht_do_measurement` с интервалом
   - Сон в 1-секундных интервалах для быстрого ответа на stop

4. **Измерение** (`dht_do_measurement`):
   - Проверка rate limiting
   - Вызов `dht_read_sensor` (bit-bang GPIO)
   - Обновление данных датчика под мьютексом

5. **Выгрузка модуля** (`dht_driver_exit`):
   - Phase 1: флаг `dht_exiting`, `proc_remove` (блокирует до закрытия файлов)
   - Phase 2: остановка потоков, освобождение памяти

### Управление прерываниями и вытеснением

Во время bit-bang чтения (~4 мс в худшем случае) прерывания отключаются с помощью `local_irq_save`/`local_irq_restore` для предотвращения искажения временных интервалов обработчиками прерываний и переключениями контекста. Это также отключает вытеснение (нет тиков таймера, нет планировщика). На Raspberry Pi 3 обработчики прерываний USB/SDIO/таймера могут занимать 100-300 мкс, превышая `PULSE_TIMEOUT_NS` (300 мкс) и повреждая чтение. Окно ~4 мс значительно ниже порога softlockup-детектора (10 секунд) и следует паттерну драйверов `w1-gpio` и `i2c-gpio` bit-bang в основной ветке ядра.

### Счётчик ссылок (kref)

Каждый датчик имеет `kref` для отслеживания активных ссылок:
- +1 при регистрации (ссылка списка)
- +1 при открытии procfs-файла (через `dht_proc_open`)
- -1 при закрытии procfs-файла (через `dht_proc_release`)
- -1 при отмене регистрации или выгрузке модуля

Когда последняя ссылка сброшена, `dht_sensor_release` освобождает все ресурсы.

### Файл конфигурации

При загрузке модуля `/etc/default/dht` читается через `filp_open`/`kernel_read`. Неизвестные опции вызывают предупреждения в `dmesg`. Отсутствие файла не является ошибкой.

## Известные ограничения

1. **Чувствительность к таймингу GPIO**: Bit-bang протокол требует микросекундной точности. Высокая нагрузка системы может вызывать сбои чтения. Автоопрос компенсирует это повторными попытками.
2. **Нет I2C/SPI**: Протокол DHT — однопроводной. Версии I2C или SPI (напр., SHT3x) требуют другого драйвера.
3. **Минимум 2 секунды между чтениями**: Датчикам DHT нужно время восстановления. Драйвер обеспечивает это для всех измерений.
4. **Чтение без прерываний**: Драйвер использует опрос (kthread), а не GPIO-прерывания. Это упрощает код, но добавляет нагрузку CPU во время чтения.
5. **Спящие GPIO-чипы не поддерживаются**: Датчики на расширителях GPIO через I2C не могут использовать этот драйвер из-за требований к таймингу.
6. **Максимум 32 датчика**: Ограничение `MAX_SENSORS` предотвращает неограниченное выделение памяти.
7. **Один датчик на GPIO-пин**: Каждый BCM-пин может иметь не более одного датчика.
8. **Нет device tree**: Датчики регистрируются динамически через procfs, а не через оверлеи device tree.

## Устранение неполадок

| Симптом                               | Причина                         | Решение                                      |
|---------------------------------------|---------------------------------|----------------------------------------------|
| `make` не находит заголовки ядра      | Нет `linux-headers`             | `sudo apt install linux-headers-$(uname -r)` |
| `make` не определяет версию ядра      | Нестандартный Makefile ядра     | Проверьте `$(uname -r)` и `KDIR`             |
| `implicit declaration of 'proc_read'` | Ядро < 5.6, нет адаптера        | Убедитесь, что `dht.c` имеет `DHT_PROC_OPS`  |
| `make` не создаёт `dht.ko`            | `obj-m` не на верхнем уровне     | Убедитесь, что `obj-m += dht.o` перед `ifdef`|
| `autoconf.h` не найден                | Ядро не подготовлено            | `make -C $(KDIR) modules_prepare`            |
| DKMS сборка не удалась                | Нет `dkms.conf` или заголовков   | `sudo apt install dkms linux-headers-...`    |
| Модуль не загружается                 | GPIO не в ядре                  | Включите `CONFIG_GPIOLIB` в конфиге ядра     |
| Чтение всегда не удаётся (status=3)   | Проводка, подтяжка или тайминг  | Проверьте проводку, добавьте подтяжку 4.7k-10k |
| `modprobe: dht not found`             | Модуль не установлен            | `make install` или DKMS установка            |
| `rmmod: Module dht is in use`         | Procfs-файл ещё открыт           | Закройте все файлы `/proc/sensors/dht/`     |
| Датчик не определяется                | Нет успешного измерения          | Проверьте проводку, попробуйте `echo 1 > measure` |
| `PDE_DATA` implicit declaration       | Ядро >= 5.17, старый код         | Используйте макрос `DHT_PDE_DATA`            |
